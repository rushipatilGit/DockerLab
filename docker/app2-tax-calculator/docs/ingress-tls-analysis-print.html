Tax Calculator — Ingress & Tomcat TLS Error Analysis

Report date: November 14, 2026
Application: Tax Calculator (Kubernetes on AWS)
Symptom: Tomcat Error parsing HTTP request header / Invalid character found in method name

Executive summary

Your Spring Boot service (service-a) runs plain HTTP on port 3000. The stack trace is not a Spring application bug. It occurs when a client sends TLS (HTTPS) handshake bytes to that HTTP port. Tomcat interprets the first bytes as an HTTP method name and fails.

Your Ingress manifest has two configuration issues that break /api routing: the backend Service port is 80 instead of 3000, and the catch-all path /(.*) is listed before /api/(.*).

Fix the Ingress for correct API traffic. Use http:// via the AWS Load Balancer hostname. Treat occasional Tomcat parse errors as noise if the app works over HTTP end-to-end.

1. Error breakdown

1.1 Log excerpt

2026-11-14T18:28:02.093Z  INFO 1 --- [demo] [io-3000-exec-10] 
o.apache.coyote.http11.Http11Processor   : Error parsing HTTP request header
 Note: further occurrences of HTTP request parsing errors will be logged at DEBUG level.

java.lang.IllegalArgumentException: Invalid character found in method name 
[0x16 0x03 0x01 0x00 0xf2 ...]. HTTP method names must be tokens

1.2 What the bytes mean

Bytes Meaning
0x16 TLS Handshake record type
0x03 0x01 TLS version in the record header
Following bytes ClientHello (certificate negotiation)

The server expected text like GET /path HTTP/1.1 but received a TLS ClientHello. Hence: "HTTP method names must be tokens".

1.3 Thread name [io-3000-exec-10]

Confirms the connection hit port 3000 — the embedded Tomcat HTTP connector in service-a.

1.4 Application name [demo]

Comes from spring.application.name=demo in the embarkx/tax-service-a container image, not from Ingress.

4. Ingress defects (root cause of broken /api)

4.1 Wrong Service port for service-a

Current (incorrect):

backend:
  service:
    name: service-a
    port:
      number: 80   # ❌ does not exist on Service

Actual Service port: 3000 only.

Effect: No endpoints for service-a:80 → NGINX cannot route /api to Spring → 503 or traffic never reaches the app.

Correct:

port:
  number: 3000

4.2 Path rule order

Current order:

  1. /(.*) → frontend (matches almost everything)
  2. /api/(.*) → service-a

With regex, the catch-all often wins for URLs like /api/price, so API calls may hit frontend instead of service-a.

Correct order:

  1. /api/(.*) → service-a:3000 first
  2. /(.*) → frontend:80 second

4.3 Rewrite behavior

With rewrite-target: /$1:

  • Request: /api/price?amount=100&country=IN
  • Upstream path becomes: /price?amount=100&country=IN (matches Spring controllers that expect /price, not /api/price)

5. Recommended Ingress manifest

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: tax-app-ingress
  namespace: default
  annotations:
    nginx.ingress.kubernetes.io/use-regex: "true"
    nginx.ingress.kubernetes.io/rewrite-target: /$1
spec:
  ingressClassName: nginx
  rules:
    - http:
        paths:
          - path: /api/(.*)
            pathType: ImplementationSpecific
            backend:
              service:
                name: service-a
                port:
                  number: 3000
          - path: /(.*)
            pathType: ImplementationSpecific
            backend:
              service:
                name: frontend
                port:
                  number: 80

Apply & verify

kubectl apply -f ingress-fixed.yaml
kubectl describe ingress tax-app-ingress
kubectl get endpoints service-a

Test URLs (use HTTP)

6. Tomcat TLS error — likely causes

These explain TLS bytes on port 3000; they are separate from the Ingress port/path bugs.

Source Scenario
Port-forward + HTTPS kubectl port-forward to 3000:3000, then browser uses https://localhost:3000
Wrong scheme on app port Any client using HTTPS against pod:3000 or mis-forwarded port
Background noise TLS port scans (less common on ClusterIP unless something exposes 3000)
Not normal Ingress Correct Ingress → HTTP → service-a:3000 does not produce this error

Note: After the first occurrence, Tomcat logs repeats at DEBUG (per log message).

For local docker-compose.yml:

Use http://localhost:3100 from the host, not https://.

Frontend .env may use VITE_API_URL=/api; the stock nginx image needs a proxy for /api unless you use VITE_API_URL=http://localhost:3100 for Docker builds.

9. Conclusion

  1. Tomcat error = HTTPS/TLS on HTTP port 3000, not a misconfigured Spring property.
  2. Ingress must route /api to service-a:3000 with /api ordered before the catch-all.
  3. Validate with curl over HTTP against the ELB hostname after applying the fixed Ingress.
  4. Occasional parse errors in logs are acceptable if user-facing HTTP traffic succeeds.
